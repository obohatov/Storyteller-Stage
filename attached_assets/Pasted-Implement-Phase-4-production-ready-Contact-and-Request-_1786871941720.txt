Implement **Phase 4: production-ready Contact and Request Full Script workflows**.

The current frontend, CMS, PostgreSQL model, security hardening, multilingual routing, visual design and SEO architecture are approved.

**Do not redesign the site.**

This phase should add two distinct communication workflows:

1. **General Contact**
2. **Request Full Script** for individual plays

Both types of submissions must be securely stored in PostgreSQL and manageable from the private CMS.

Email notification to the author should be added as a secondary delivery channel, but the database must remain the reliable source of truth.

The site has four locales:

* English: `en`
* Ukrainian: `uk`
* Russian: `ru`
* Dutch: `nl`

---

# 1. General principle

Do NOT combine Contact and Request Full Script into one generic form.

They serve different audiences and collect different information.

### General Contact

For:

* readers
* publishers
* translators
* festivals
* collaboration
* other general enquiries

### Request Full Script

Primarily for:

* theatres
* directors
* producers
* festival programmers
* publishers
* other theatre professionals interested in a specific play

---

# 2. PostgreSQL message model

Create an appropriate database structure for incoming enquiries.

A clean approach could use either:

* one `messages` table with a message type and type-specific fields, or
* separate `contact_messages` and `script_requests` tables.

Choose the simplest maintainable structure.

All submissions should store at minimum:

* id
* type
* locale
* name
* email
* message
* status
* created_at

Where appropriate also store:

* organization
* role / position
* city
* country
* enquiry category
* play_id
* intended use

Use foreign keys where appropriate.

Do not store unnecessary personal data.

---

# 3. Message statuses

Keep the workflow simple.

Support statuses such as:

* `new`
* `read`
* `archived`

For Script Requests, optionally also support:

* `replied`

only if this can be added cleanly without overcomplicating the CMS.

Do not create a CRM or ticketing system.

# 6. Request Full Script workflow

On each Play Detail page, where the CMS setting is:

**Full script available on request**

show a prominent:

**Request Full Script**

CTA.

Preserve the existing Play page design.

Clicking the CTA should open either:

Do not redesign the page around the form.

# 7. Script Request form

The form must automatically know which play is being requested.

The visitor must NOT need to type the play title manually.

Store the actual `play_id`.

Display the localized play title clearly in the form.

Collect:

### Required

* Name
* Email
* Organization / Theatre
* Country
* Intended use
* Message

### Optional

* Role / position
* City

### Intended use

Stable internal values with localized display labels:

* Reading / evaluation
* Production
* Festival
* Publishing
* Translation
* Education
* Other

Do not allow an arbitrary play ID from the client to bypass validation.

Verify server-side that the requested play exists and that the relevant translation is publicly available.

---

# 8. Respect Script Availability

The CTA behavior must respect the CMS setting.

### Full text public

Do not unnecessarily ask the visitor to request the script if the full script is already public.

### Excerpt only

A Request Full Script CTA may be shown if appropriate.

### Full script available on request

Show the Request Full Script CTA prominently.

Do not expose private/full script content through the API simply because a request was submitted.

Submitting a request does NOT automatically grant access to a private script in this phase.

The author will respond manually.

---

# 9. Four-language UX

All form labels, validation messages, confirmation messages and error states must work in:

* EN
* UA
* RU
* NL

Keep internal database enum values language-neutral.

A user submitting from a Russian page should see Russian UI.

A user submitting from a Dutch page should see Dutch UI.

Also store the locale from which the form was submitted.

---

# 10. Success state

After successful submission, show a clear localized confirmation.

For example, conceptually:

### Contact

“Thank you. Your message has been sent to Sofia Bohatova.”

### Script Request

“Thank you. Your request for [Play Title] has been received.”

These are examples only.

Use natural localized copy.

Do not claim that an email has been delivered unless email delivery actually succeeded.

The database submission itself should be treated as successful once safely stored.

Prevent accidental double-submission while the request is processing.

---

# 11. Failure state

If submission fails:

* keep the user's entered form content where practical;
* show a clear localized error;
* do not expose database/server details;
* allow the user to try again.

Do not display raw stack traces or internal errors.

---

# 12. Spam protection

Implement lightweight, privacy-conscious spam protection.

At minimum:

* server-side rate limiting
* hidden honeypot field
* reasonable field-length limits
* reject obviously automated malformed requests

Do NOT add an intrusive CAPTCHA unless necessary.

Do not add third-party tracking merely for spam prevention.

If you believe CAPTCHA is necessary, stop and explain why before adding it.

---

# 13. Security

All public message-submission endpoints must:

* accept only expected fields
* validate server-side
* prevent SQL injection through parameterized/database-safe operations
* sanitize plain-text fields where appropriate
* rate-limit abusive requests
* never expose admin data

The admin message endpoints must use the existing `requireAdmin` middleware.

Anonymous users may submit forms but may never read submissions.

---

# 15. Important delivery behavior

Database persistence and email notification must be decoupled.

Correct flow:

1. Validate submission.
2. Save it successfully to PostgreSQL.
3. Attempt email notification.
4. Return an appropriate result.

If database save succeeds but email notification fails:

* DO NOT lose or delete the enquiry;
* keep it visible in the CMS;
* log the email delivery failure safely;
* do not tell the visitor that their entire submission failed if it is safely stored.

The CMS must remain the reliable inbox.
